======================================================================
1. KERNUNTERSCHIED P1 -> P2
======================================================================

P1 (Half-Life-2-Engine):
  Ein Button ist ein Entity-Zoo aus prop_static + prop_dynamic +
  mehreren trigger_-Entities + logic_-Steuerung + Licht + Sound.

P2 (eigene Engine):
  Ein Button ist EINE Entity und EIN Wire:

    "OnPressed" "Door1\x1bOpen\x1b\x1b0.5\x1b-1"

Das ist der ganze Unterschied, und er ist gewaltig: die Sprache
wird um Groessenordnungen kleiner.

4. SYNTAX-DESIGN (Vorschlag)
======================================================================

4a. Entities
-----------
Der Blockname bestimmt die Rolle, ein optionaler type= das konkrete
Modell.  Positionsangaben sind Pflicht, damit der Compiler nichts raten muss.

  button open_btn["Druecke mich";
                  type="prop_floor_button";
                  pos="-228 -340 72";
                  yaw="0";]

  door   door1["Testkammertuer"; pos="0 2 -64"; yaw="270";]

  cube   cube1["Wuerfel"; pos="-144 -272 83"; yaw="342.5";]

  turret turret1["Turm"; pos="-92 110 64"; yaw="89.5";]

  start  player["Start"; pos="-95 -320 65"; yaw="90";]

4b. Wiring
----------
Gegenueber 3.0 AENDERT sich die Bedeutung von delay!

  wire["Ziel.Input", "Parameter", delay="0.5"];

erzeugt das 5-Feld-ESC-Format:

  Feld 1  Ziel-Entity        "Door1"
  Feld 2  Input              "Open"
  Feld 3  Parameter          ""      <- der Wert aus Parameter
  Feld 4  Delay in Sekunden  "0.5"  <- der Wert aus delay=
  Feld 5  Aufruf-Anzahl      "-1"    (einmalig)

FEHLER IN 3.0 (jetzt behoben):
  In 3.0 wurde delay in Feld 3 geschrieben. Das ist falsch.
  Belegt ist es durch map_ref.vmf:

    "OnPressed" "Door2\x1bSetAnimation\x1bOpen\x1b0\x1b-1"
       Feld 3 = "Open"  -> Parameter (Animationsname)
       Feld 4 = "0"     -> Delay

  In 3.0 wuerde daraus werden:
    "Door2\x1bSetAnimation\x1b2\x1b0\x1b-1"   <- Parameter="2", Delay=0

  Warum das in 3.0 nicht auffiel: die Verzoegerung war einfach 0,
  also "unsichtbar falsch".

4c. Weiterhin benoetigte Verbindungs-Arten
-------------------------------------------
Aus door_ref_01 und map_ref.vmf kommen vor:

  OnPressed     Button -> Tuer (SetAnimation Open bzw. Open)
  OnUnPressed   Button -> Tuer (Close)
  OnDeploy      Portal/Tuer -> Turret (FireBullet)
  OnTipped      Turret -> Light (TurnOff)

5. LICHT — DER GRUND FUER "KOMPLETT DUNKEL"
======================================================================

vbsp erzeugt NIE Lichtmaps. vrad erzeugt sie.
Ohne vrad ist die Map schwarz, egal wie viele light-Entities sie hat.

Der Compiler soll deshalb IMMER automatisch erzeugen:

  light_environment   origin = Kammer-Mitte, hoch
                      pitch  = -90
                      _light = "255 255 255 200"

  fuer jede Kammer zusaetzlich ein bis zwei `light`-Entities.

Beweis aus der Referenz:
  vbsp EXIT 0, vrad EXIT 0 -> "7 direct lights", lightdata 603 524 bytes
  Das sind u. a. light1 mit _light "255 255 255 350" und _quadratic_attn 1.

7c. 4.0 -> 5.0 KONVERTIEREN
=====================================================================

    python scripts/map4_to_vms.py alt.vms -o neu.vms

Der Konverter ueberbrueckt die Unterschiede, die 4.0 zu 5.0 trennen:

  4.0                                   5.0
  ----------------------------------   -------------------------------
  layout{ axis["x"]; passage["256"] }  layout{ chambers="3", width=... }
  chamber_00{ sizex=["1024"]; ... }    Kammern werden ZUSAMMENGEFASST
  pos="512, 256, 64"  (Komma)           pos="512 256 64"  (Leerzeichen)
  light_01 je Kammer neu                light_01, light_01_02, _03
  material{ floor["hl2/..."] }          Faellt weg (P1-Materialien)
  door["door_01"]  (Name im Listwert)   door_01[... pos=...]

NICHT 1:1 und im Ausgabekopf gemeldet:
  - material{} verworfen: P1-Materialien gibt es in P2 nicht
  - Tueren ohne pos=: Trennwand-Position wird berechnet
  - rotator axis=/speed= gehen nicht 1:1 auf func_rotating

Belegt: examples/test4.vms -> test4_converted.vms, dann
vbsp/vvis/vrad EXIT 0, 1 438 968 Bytes BSP, 10 Entities, 1 Wire
("OnPressed" -> door_01|Open||0|-1).

9. GEOMETRIE: layout{} und solid{}
======================================================================

VMFScript baut KOMPLETTE TESTKAMMERN, nicht nur Entities. Geometrie
entsteht in zwei Bloecken:

layout{
  chambers["2", width="512", length="512", height="256",
           door_width="64", door_height="96", origin="0 0 0"];
}

  chambers   Anzahl Kammern, hintereinander entlang +Y.
             "1" = eine Kammer OHNE Durchgang.
             "0" = gar keine Kammer, nur die solid{}-Bloecke. Das ist der
             Import-Modus: bei aus einer VMF uebernommener Geometrie
             wuerde eine zusaetzliche Huelle die Form veraendern.
  width/length/height   Kammermasse in Hammer-Einheiten (1 Tile = 64).
  door_width/door_height   Durchgang in der Wand zwischen zwei Kammern.
  origin                Ursprung der Geometrie.

solid{
  brush_01["0 0 0", "128 0 128", mat="TILE/WHITE_WALL_TILE003B"];
}

  Ein einzelner achs-paralleler Brush als x0 y0 z0 / x1 y1 z1.
  lo/hi duerfen in beliebiger Reihenfolge stehen. mat optional.

Beispiel (examples/test_chamber_two.vms) ergibt 15 Solids, 7 Entities,
vbsp/vvis/vrad EXIT 0, 350 020 Bytes BSP.

--- Warum zwei Kammern statt einer mit Durchgang ---
Eine Oeffnung braucht SOLID-Massen auf BEIDEN Seiten. Mit nur einer
Kammer endet sie im leeren Raum: vbsp bildet kein Portal, schreibt
keine .prt, jede Entity wird als "leaked" gemeldet und vvis scheitert
mit EXIT 1. Mit zwei Kammern ist das behoben (belegt: 14 Brushes,
vbsp/vvis/vrad EXIT 0, 202 824 Bytes BSP, kein "leaked").

--- Warum eine Wand als VIER Brushes und nicht als Panel-Grid ---
Ein Grid aus 72 einzeln beruehrenden Brushes erzeugt keine durchgehende
CONTENTS_SOLID-Flaeche am Portal. Deshalb baut wall_with_opening()
die Wand als vier grosse Brushes: unterhalb, oberhalb, links, rechts
der Oeffnung. Portal-tauglich und deutlich kleiner.

--- Roundtrip: Geometrie kommt zurueck ---
func_detail / func_detailwall / func_brush werden als solid{}-Bloecke
uebersetzt, jede Brush-BBox mit ihrem Material. Belegt an
door_ref_01.vmf: 48 func_detail -> 48 solid-Zeilen -> 48 Solids mit
exakt den Panel-Massen der Quelle (x -64..64, y -16..18, z -64..64),
vbsp EXIT 0. map_ref.vmf hat 49 (48 Wand + 1 Schild/func_brush).

Nicht-achsenparallele Brushes werden zu Quadern vergroessert - fuer
exakte Formen Hammer benutzen.

--- Materialien (nur belegte, aus den Referenzmaps) ---
  TILE/WHITE_WALL_TILE003B              Wand-Panels
  CONCRETE/CONCRETE_MODULAR_FLOOR001C  Boden
  TILE/OBSERVATION_TILECEILING001A      Decke
  TOOLS/TOOLSNODRAW                     unsichtbare Seiten
P2 hat KEINE "WHITE_FLOOR_TILE002B" oder "WHITE_CEILING_TILE003B";
solche Namen ergeben "Material not found!" und schwarze Flaechen.

======================================================================

Aufruf:
  python map5_compile.py map.vms                  -> map.vmf
  python map5_compile.py map.vms --testroom       -> + Testkammer
  python map5_compile.py map.vms --compile        -> + vbsp/vvis/vrad

Beispiel: examples/test_floor_button_door.vms

Ergebnis (real ausgefuehrt):
  7 Entities, 2 Wires, 6 Solids (Testkammer)
  vbsp EXIT 0, vvis EXIT 0, vrad EXIT 0
  test_fbd.bsp 942 032 Bytes

Erzeugte Entities:
  info_player_start      targetname=player      (setzt den Portalgun daneben)
  weapon_portalgun       targetname=player_gun
  light_environment      mit _ambient (verhindert die schwarze Map)
  light x2               _light "255 255 255 350" / 300
  prop_testchamber_door  targetname=door1
  prop_floor_button      targetname=btn

Erzeugte Wires:
  "OnPressed"   "door1\x1bOpen\x1b\x1b0.5\x1b-1"
  "OnUnPressed" "door1\x1bClose\x1b\x1b1\x1b-1"

Zwei Fehler, die dabei gefunden und behoben wurden:

1. light_environment braucht laut base.fgd (Zeile 2951) zwingend
   _ambient und _AmbientScaleHDR. Ohne sie kommt vrad mit
   "unknown light specifier type -". Ausserdem darf kein "angles"
   geschrieben werden, weil pitch ein eigener Key ist.

2. Testkammer-Waende mit 64 Einheiten Staerke erzeugen keine
   gueltigen Portale: vbsp meldet "FindPortalSide: Couldn't find a
   good match for which brush to assign to a portal" und vvis bricht
   mit EXIT 1 ab. Mit 8 Einheiten Wandstaerke laufen alle drei
   Tools mit EXIT 0 durch.

Hinweis fuer echte Maps: bei --testroom ist der Raum
0..1024 / 0..1024 / 0..512. Ohne --testroom kommen die Positionen
unveraendert in die VMF und muessen zur Hammer-Geometrie passen.
